
# Technical Brief & Architecture Use Case: Liberia Marketplace MVP

## 1. Project Overview & Architectural Philosophy

**LibMarket** is a mobile-first community marketplace designed for high-density usability under strict infrastructure constraints. Because our target demographic operates in an environment characterized by **high mobile data costs, intermittent electrical power, and fluctuating cellular network connectivity**, our core engineering philosophy is **Defensive Design for Low-Bandwidth Infrastructure**. The application must prioritize aggressive asset optimization, minimal payload delivery, and elegant fault tolerance over heavy real-time data streaming.

A secondary design mandate is **Low-Literacy Accessibility**: the UI leads with icons over text, enforces large touch targets (≥44px), supports voice-to-text input for listing descriptions and search, and ships in both **English and Liberian Pidgin** via a runtime language toggle.

---

## 2. Core Architectural Principles

* **Mobile-First SPA:** The client is a React 19 Single-Page Application built with Vite. All pages are lazy-loaded via `React.lazy` to keep the initial bundle small. There is no server-side rendering; fast perceived load is achieved through skeleton screens and immediate cache population.

* **Offline-First Resilience:** If a network request fails or times out due to a weak cellular signal, the client falls back to cached `localStorage` data without breaking UI state, and surfaces a non-obtrusive toast: *"Viewing offline listings. Prices and availability will refresh once connection stabilizes."*

* **Asset Economy:** All user-submitted media is compressed client-side (via `imageCompression.ts` + `sharp` server-side) before transmission. The media pipeline serves WebP-converted assets. Cloudinary is used in production; local `uploads/` directory is used in development.

* **Liberian Infrastructure Assumptions:** Phone numbers are the primary identity anchor (9-digit Liberian format). Payments are exclusively mobile money (Orange Money, MTN MoMo, Lonestar Money) — no card rails. Location filtering is scoped to Liberia's **15 counties**.

---

## 3. High-Level System Architecture

```
[ Client: React 19 + Vite SPA ]
       │
       ├── withCredentials: true (httpOnly cookie auth)
       ├── X-CSRF-Token header (non-GET mutations)
       │
       ▼
[ Backend: Node.js + Express API  |  Port 5000 ]
       │
       ├──► [ Auth: JWT in httpOnly cookie ]
       │         └── Token revocation via token_version column
       │
       ├──► [ Database ]
       │         ├── SQLite (development / test in-memory)
       │         └── PostgreSQL + SSL (production)
       │
       ├──► [ Media Pipeline ]
       │         ├── multer + sharp  (local dev)
       │         └── Cloudinary      (production, USE_CLOUD_STORAGE=true)
       │
       └──► [ Real-Time Layer: Socket.io ]
                 └── JWT auth via cookie on handshake
                     Tracks: userSockets map, conversationRooms map
```

## 4. Data Model & Schema

The schema is managed via **Sequelize migrations** (`backend/migrations/`). `sequelize.sync()` is disabled; all schema changes require a migration file. The test environment uses an in-memory SQLite instance (`storage: ':memory:'`) that is force-synced and wiped between each test.

### Core Entities

    id                        UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    email                     VARCHAR(255) UNIQUE,              -- optional

    message_type         VARCHAR(20) DEFAULT 'text',  -- text | image | offer | system
    is_read              BOOLEAN DEFAULT FALSE,

    deleted_by_sender    BOOLEAN DEFAULT FALSE,

## 5. API Surface

All routes are prefixed `/api`. Auth uses httpOnly cookie (`token`). CSRF protection is required on all non-GET state-changing endpoints (except `/api/auth/*`); the frontend fetches a bootstrap token from `GET /api/csrf-token` on startup.

| Prefix                         | Auth Required | Notes                                           |
|--------------------------------|---------------|-------------------------------------------------|
| `/api/auth/register`           | No            | Phone + password; phone normalized to 9-digit   |
| `/api/auth/login`              | No            | Returns JWT in httpOnly cookie                  |
| `/api/auth/logout`             | Yes           | Clears cookie                                   |
| `/api/auth/me`                 | Yes           | Get current user (no rate limit)                |
| `/api/auth/forgot-password`    | No            | Issues SHA256-hashed reset token (10-min TTL)   |
| `/api/auth/reset-password/:token` | No         | Consume token and set new password              |
| `/api/auth/update-password`    | Yes           | Requires current password verification          |
| `/api/users`                   | Admin only    | List all users                                  |
| `/api/users/:id`               | Admin only    | Get / update / delete any user                  |
| `/api/users/profile`           | Yes           | Get or update own profile, upload avatar        |
| `/api/users/payment-preferences` | Yes         | Save preferred mobile money accounts            |
| `/api/csrf-token`              | No            | Bootstrap CSRF token (GET only)                 |
| `/api/products`                | Optional      | Public browse; write ops need `seller` role     |
| `/api/products/search`         | No            | Full-text on title, description, location       |
| `/api/categories`              | No            | Read-only for public; admin write               |
| `/api/offers`                  | Yes           | Buyer initiates; cron job auto-expires stale    |

| `/api/dashboard`               | Yes           | Seller/buyer analytics                          |

| `/api/mobile-money`            | Yes           | Link/manage mobile money accounts               |

## 6. Primary Use Case: Item Listing & Discovery Loop

### Use Case ID: UC-001 (Core Loop)

* **Actors:** Seller, Buyer, Client Application, Backend API, Storage Service.
* **Preconditions:** Seller is authenticated via phone number + password. Buyer has the application open (online or offline).

### A. Listing Creation (Seller Side)

1. Seller navigates to `/products/add` (protected: `seller` or `admin` role).
2. Seller inputs title, price (LRD or USD), description, county location, category, and captures/selects an image.
3. **Client-Side Optimization Intercept:** `imageCompression.ts` resizes and compresses the raw image before transmission. The voice input component (`VoiceRecorder.tsx`) can populate the description field via speech-to-text for low-literacy sellers.
4. The client submits a single `multipart/form-data` payload containing listing metadata and the compressed image binary. The `Content-Type` header is omitted from the Axios request so the browser sets the correct multipart boundary automatically.
5. The backend processes the binary through `sharp` (resize + WebP conversion), stores the result (Cloudinary in production, `uploads/` in dev), and inserts the record.

### B. Discovery & Data Fetching (Buyer Side)

1. Buyer opens the home feed or `/products`.
2. The client immediately populates the UI from `localStorage` cache to ensure instantaneous visual readiness (skeleton cards render during background fetch).
3. A background async fetch is dispatched with a 10-second Axios timeout.
4. **Scenario A (Network Success):** Fresh data arrives. Client updates the cache and re-renders the feed.
5. **Scenario B (Network Timeout/Failure):** The client catches the error silently, retains cached data on-screen, and surfaces a toast notification: *"Viewing offline listings. Prices and availability will refresh once connection stabilizes."*

### C. Transaction Handshake (In-App Messaging)

1. Buyer selects a product and opens the detail view (`/products/:id`).
2. Buyer initiates contact via the in-app "Message Seller" button, which creates or resumes a `Conversation` record linking buyer, seller, and product.
3. The `MessageThread` page (`/messages/:id`) opens a Socket.io connection. Messages are delivered in real-time to both parties. Typing indicators and read receipts are tracked server-side via `conversationRooms` and `typingUsers` maps in `socketManager.js`.
4. Buyer can alternatively submit an **Offer** (a counter-price proposal) via the `MakeOfferModal`. Offers expire automatically via a `node-cron` job (`src/cron/offerExpirationJob.js`).
5. Accepted offers progress to a **Payment** flow: the buyer selects their registered mobile money account (Orange Money, MTN MoMo, or Lonestar Money) and confirms. The seller receives an SMS notification (Twilio) and an in-app notification.

## 7. Security Model

* **JWT** stored in `httpOnly`, `SameSite=Strict` cookies. Never exposed to `document.cookie` in the frontend.
* **Token revocation** via `token_version` on the User model — incrementing this value on logout-all or password change invalidates all existing sessions without a blocklist.
* **CSRF** protection via `csurf` on all state-changing routes; skipped in the `test` environment.
* **Rate limiting** (production): auth endpoints 5 req/15 min, all other API routes 100 req/15 min. Keyed by phone number (if present in body) or IP.
* **Helmet** sets CSP, HSTS (1 year + preload), `X-Content-Type-Options`, and hides `X-Powered-By`.
* **Input sanitization**: `xss-clean`, `express-mongo-sanitize`, `hpp` (HTTP Parameter Pollution), and `Joi` schema validation on auth and product routes.
* **Passwords** hashed with `bcryptjs` at **12 salt rounds**. Password strength enforced client-side via `PasswordStrengthMeter.tsx`. Password resets use a 20-byte random token, SHA256-hashed before DB storage, with a 10-minute expiry. Users must supply the current password to change it via the update-password endpoint.
* **Image uploads** validated for MIME type and size (max 5 MB configured via `MAX_FILE_SIZE` env var).

## 8. Frontend Context & State Architecture

```
<ErrorBoundary>
  <AuthProvider>          ← JWT session verified via /api/auth/me on mount
    <LanguageProvider>    ← 'en' | 'pidgin' toggle, persisted to localStorage
      <ToastProvider>     ← Global toast notifications
        <Router>
          <AppContent />  ← HamburgerMenu + BottomNav hidden on /, /login, /register
        </Router>
      </ToastProvider>
    </LanguageProvider>
  </AuthProvider>
</ErrorBoundary>
```

All API calls flow through a single Axios instance (`utils/api.ts`) configured with `withCredentials: true`. The CSRF token interceptor attaches `X-CSRF-Token` to every mutating request and automatically retries on a 403 CSRF error with a freshly fetched token.
